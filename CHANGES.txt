THE BUG (from your production log — real, not theoretical)
-------------------------------------------------------------
Your deploy log showed this exact error repeated ~10 times, once per route
file, right as every router was mounting:

  ValidationError: A Store instance must not be shared across multiple
  rate limiters. Create a new instance of RedisStore (with a unique
  prefix) for each limiter instead.
  code: 'ERR_ERL_STORE_REUSE'

I opened src/middleware/rateLimiter.js and confirmed it directly: a single
`redisStore` object was constructed once, then handed to eleven separate
`rateLimit({ store: redisStore, ... })` calls (authLimiter, apiLimiter,
marketplaceLimiter, registerLimiter, passwordResetLimiter,
dataExportLimiter, searchLimiter, uploadLimiter, chatLimiter,
callInitiationLimiter, dynamicLimiter). express-rate-limit v7+ explicitly
rejects sharing one store instance across multiple limiters. There was
also a second, related bug: `const RedisStore = require('rate-limit-redis')`
grabs the whole module object, not the class — rate-limit-redis v4 exports
RedisStore as a named export. Depending on the exact resolved package
version this manifests as either "RedisStore is not a constructor" or the
store-reuse error above (I actually got the "not a constructor" variant
locally and the reuse error is what your production log showed — same
root defect, two different failure faces depending on environment).

I did not stop at reading the error — I ran the actual module in Node
before and after the fix to confirm it, not just read the code and assume:

  BEFORE (reproduced locally):
    ❌ Redis connection failed: RedisStore is not a constructor
    (module still "loaded", but every limiter silently got an in-memory
    fallback store instead of Redis — meaning rate limiting resets on
    every server restart / doesn't work across multiple server instances,
    silently, no error visible unless you go looking)

  AFTER:
    ✅ Redis connected for rate limiting
    MODULE LOADED OK
    authLimiter : function
    apiLimiter : function
    ...(all 11 limiters loaded as real functions, zero errors)

FIX
----
src/middleware/rateLimiter.js — two changes:
  1. `const { RedisStore } = require('rate-limit-redis');` (named import,
     matches the actual package export shape)
  2. Each limiter now calls `makeStore('<unique-name>')`, which creates
     its OWN RedisStore instance with a unique Redis key prefix
     (rate-limit:auth:, rate-limit:api:, rate-limit:chat:, etc.) instead
     of all eleven sharing one instance.

WHY THIS MATTERS FOR YOUR SYMPTOM
------------------------------------
I can't prove this is THE cause of "first send doesn't go through, works
after refresh" without seeing it happen live — but the profile fits: this
error was firing during EVERY server boot, on every route file, for what
looks like every deploy you've shown me. A rate limiter that fails to
construct correctly is exactly the kind of thing that could make a
request silently misbehave on the first attempt in a way that isn't
visible in the response body, and this is a definite, confirmed, verified
bug regardless — worth having fixed either way.
