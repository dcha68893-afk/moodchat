WHY ROUND 1 WASN'T ENOUGH FOR YOUR PRODUCTION DB
-------------------------------------------------
My first pass was verified against a brand-new, empty database, where every
migration runs fresh in order. Your production database has real deploy
history, tracked in a SequelizeMeta table BY FILENAME ONLY — editing a
migration file's content does nothing if Sequelize already has that filename
recorded as "done" from an earlier deploy. Your deploy log showed the batch
now progressing further than before but still dying partway with:
  ERROR: column "groupId" referenced in foreign key constraint does not exist
which meant your actual Messages table never got a groupId column in the
first place. That's now fixed defensively (see #1 below), and I traced the
migration chain all the way through to a clean, complete, zero-error run
(verified against a real Postgres 16 instance) — including confirming your
two direct symptoms from the logs:
  - `relation "offline_message_queue" does not exist` on message-queue flush
  - `Message 112 undelivered after 10s — expected ack from uid=5` (a message
    accepted from the sender but never confirmed delivered to the recipient)
Both trace back to the SAME root cause: the migration batch was dying before
reaching the migrations that create those things, because of the bugs below.

FIXES IN THIS ROUND
--------------------
1. migrations/20260118080600creategroup.js (+ 2026118080600creategroup.js)
   Made defensive: Messages.groupId is now added if missing (not assumed to
   already exist from createmessages.js, which your DB's history may have
   skipped), and the FK constraint is only added if it isn't already there.
   This directly fixes the "column groupId referenced in foreign key
   constraint does not exist" error from your deploy log.

2. migrations/2026999990001_add_messages_perf_indexes.js
   Your app has its OWN separate runtime migration system (in
   src/models/index.js, the "[Migration] STEP 1-6" logic visible in your
   deploy log) that adds columns like Messages.chatId AFTER the server
   process boots. `npx sequelize-cli db:migrate` runs as a one-off
   subprocess BEFORE that — so on your database, chatId genuinely doesn't
   exist yet when this migration runs, and it was crashing the whole batch.
   Now it checks first and skips its chatId-based indexes gracefully if
   chatId isn't there yet (they'll still get created by your runtime system
   or a later deploy).

3. migrations/2026999990013_add_message_lifecycle_fields.js
   Same root cause as #2 — its status-backfill step referenced isRead/
   deliveredAt, which also don't exist yet at this point in your DB's
   history. This was blocking clientMessageId from ever being added — the
   column your idempotent first-send logic depends on. Now the column
   creation always runs; only the optional backfill is skipped if those two
   columns aren't there yet.

4. migrations/2026999990000_create_chats_and_chat_participants.js (renamed
   from 2026999990017, see note above)
   Renumbered to run early enough to exist before
   2026999990002_create_chat_polls.js references it.

5. migrations/20260701000001-add-call-composite-indexes.js
   src/models/Call.js
   Calls.participants (the base array of call participant user IDs) was
   never added anywhere — only the derived participantsJoined/
   participantsLeft arrays were. This migration's GIN index on it was
   failing with "column participants does not exist", which — same as #1 —
   silently blocked every migration after it in your deploy, including the
   ones that create offline_message_queue. Fixed in two places: the
   migration now adds the column defensively, and Call.js's own self-heal
   list (the pattern already used for participantsJoined etc.) now includes
   it too, so it's covered regardless of which path creates it first.
