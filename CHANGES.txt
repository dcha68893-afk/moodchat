moodchat backend — first-message-send / reply fix set
=======================================================
Drop these files into the same relative paths in the moodchat repo
(migrations/... and src/utils/ensureSchema.js), overwriting the existing
ones, then run: npm run db:migrate  (or just restart the server — the
self-heal path in ensureSchema.js also picks up the role/settings fix).

All of this was found and verified by actually running the backend
(Postgres 16 + Redis) against a genuinely fresh database, not by reading
code alone — see the in-file comments for exact reproduction steps and the
error each fix resolves.

1. FK case-sensitivity bugs (multiple files)
   migrations/20260118080100createtokens.js (+ its 2026118... duplicate)
   migrations/20260118080200createprofile.js (+ duplicate)
   migrations/20260118080300createfriends.js (+ duplicate)
   migrations/20260118080500createstatus.js (+ duplicate)
   migrations/20260118080700creategroupmembers.js (+ duplicate)
   migrations/20260118080900createreadreceipts.js (+ duplicate)
   migrations/20260118081100createcalls.js (+ duplicate)
   migrations/2026999990002_create_chat_polls.js
   migrations/2026999990005_create_live_location_sessions.js
   -> `references: { model: 'users' }` (and 'messages', 'group') used the
      wrong case. The real tables are "Users", "Messages", "Groups" — Postgres
      treats these as different relations. On a genuinely fresh database this
      aborts the WHOLE migration batch at the second migration ever run.
      Because `npm start` runs migrations as `(npm run db:migrate || true)`,
      that fatal failure is silently swallowed and the server boots anyway,
      permanently missing almost the entire schema.

2. Migration ordering bug
   migrations/20260118080400createmessages.js (+ duplicate)
   migrations/20260118080600creategroup.js (+ duplicate)
   -> Messages.groupId referenced the Groups table two migrations before
      Groups was created. Fixed by creating the column plain and adding the
      FK constraint later, once Groups exists.

3. Schema-drift self-heal gap (this is what was actually blocking
   registration — confirmed live: every POST /auth/register call 500'd)
   src/utils/ensureSchema.js
   -> Users.role and Users.settings are defined on the Sequelize model and
      added by migrations/2026999990015_add_users_role_and_settings.js, but
      that migration only runs if every earlier migration in the batch also
      succeeds. This file is the app's own "belt and suspenders" self-heal
      list for exactly this class of drift, and these two columns were
      missing from it. Added both.

4. Missing durable migration for the core messaging tables
   migrations/2026999990017_create_chats_and_chat_participants.js  (NEW)
   -> `chats` and `chat_participants` — the tables directChatResolver.js /
      POST /chats/bootstrap / POST /messages depend on for every 1:1
      conversation — had NO migration anywhere in the repo. They only ever
      got created by a best-effort sequelize.sync() fallback at boot, which
      is NOT reliable: one clean boot created both tables and a full
      register -> bootstrap -> send -> reply flow worked end-to-end
      (verified over both REST and a real Socket.IO client); an otherwise
      identical boot right after left chat_participants missing entirely,
      and the very first bootstrap call any user made failed with
      `relation "chat_participants" does not exist` — an intermittent
      "first message doesn't work" symptom. This migration makes both
      tables durable and idempotent (CREATE TABLE IF NOT EXISTS, guarded
      FK/index creation), matching src/models/Chats.js and
      src/models/ChatParticipant.js exactly.

5. UUID/INTEGER type mismatches blocking the migration batch
   migrations/20260604000001-create-marketplace-cart.js
   migrations/20260608000001-fix-tools-marketplace-schema.js
   -> marketplace_carts.user_id and Tools.seller_id (plus Tools.saved_by /
      purchased_by arrays) were typed UUID but Users.id is a plain
      auto-increment INTEGER. This is unrelated to messaging on its face,
      but it matters because it's a hard blocker in the strict production
      path (`npm run start:render` -> `db:migrate:render && npm run prod`,
      which does NOT swallow a failed migration) — it sat directly between
      the working early migrations and every migration after it, including
      fix #4 above. Fixed both to INTEGER.

What was verified end-to-end (not just read):
- Full migration chain runs clean through every messaging-critical table
  (Users, Tokens, Profile, Friends, Messages, ChatPages, Status, Groups,
  GroupMembers, ReadReceipts, TypingIndicators, Calls, Moods, Media, Tools,
  Attachments, marketplace_carts) and on into later, unrelated migrations.
- Two fresh users can register, log in, bootstrap a first-time conversation
  they've never had before, send the first message, and receive a reply —
  confirmed via direct REST calls AND via a real Socket.IO client watching
  msg:new / message:new / message:sent fire correctly on both sides.

Known remaining issue NOT fixed here (out of scope — unrelated subsystem):
migrations/20260701000001-add-call-composite-indexes.js fails with
`column "participants" does not exist` on a fresh database, blocking
migrations after it in the strict production path. This is a Calls-feature
performance index, unrelated to messaging send/reply.
